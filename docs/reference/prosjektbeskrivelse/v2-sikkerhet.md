# V2 — Do-not-harm (DNSH)

**Status:** første røffe utkast · **Sideanslag:** ~1 · **Vurderes under:** Virkninger  
**Forelder:** `ipn-hovedokument.md` §5 · **Grunnlag:** sannhetsserum §4

## Søknadstekst

Prosjektet skal bidra til bedre ressursbruk, men det må ikke løse ett problem ved å skape et
annet. Derfor skal VERIFIED ha do-not-harm som en del av modellen, ikke som et vedlegg på siden.

Modellen skal aldri kåre "beste valg" bare fordi ett tall er godt. Lav CO2 kan være bra, men
ikke hvis produktet får kort levetid, dårlig dokumentasjon eller høy teknisk risiko. Lav pris
kan være bra, men ikke hvis valget gir mer vedlikehold, mer utskifting eller flere avvik.

Do-not-harm håndteres med en enkel risikotabell:

| Risiko | Hvordan prosjektet skal håndtere den |
| --- | --- |
| Lav CO2 gir kortere levetid | Levetid, vedlikehold og teknisk risiko skal inngå som egne kriterier. |
| Billigste valg gir mer forbruk | Modellen skal sammenligne nykjøp med reparasjon, vedlikehold og ombruk der det er relevant. |
| Svake data ser sikre ut | Datastatus skal vises tydelig: mangler, kandidat, estimert eller verifisert. |
| Store leverandører får fordel fordi de har bedre dokumentasjon | Produktprestasjon og dokumentasjonskvalitet skal skilles. Manglende dokumentasjon skal vises, ikke skjules. |
| Systemet blir mer arbeid for SMB | Pilotene skal måle tidsbruk og om grunnlaget kan brukes uten spesialistkompetanse. |
| Bankdata brukes feil | Banksporet skal avgrenses til prosjekt- og produktdokumentasjon, ikke personprofilering. |
| Ombruk gir teknisk risiko | Egnethet, restlevetid, transport og ansvar skal vurderes før ombruk får god score. |
| Kjemikalier eller helsefare overses | CO2 skal ikke stå alene. FDV, EPD, produktkrav og dokumentasjonshull skal med. |
| Reparasjon brukes som pynt | Reparasjon og vedlikehold skal måles som utsatt utskifting, spart materiale og teknisk forsvarlighet. |
| Effekter loves uten baseline | Hver effekt skal ha baseline, indikator, datakilde og ansvarlig måler. |

VERIFIED skal også unngå falsk presisjon. En poengsum kan virke mer sikker enn den er.
Prosjektet skal derfor vise datakilder, datakvalitet, antakelser og begrensninger. Brukeren
skal se når et valg er godt dokumentert, og når det bare er et foreløpig anslag.

## Åpne avklaringer

- [ ] Hver DNSH-rad trenger et konkret etterprøvbart mottiltak.
- [ ] Avklar om "S mangler" i tidligere notater betyr sosiale minstekrav.
- [ ] Koble DNSH-radene til målepunkter i WP/pilot når WP-delen tas opp igjen.

## Språknotat

Dette skal være praktisk språk. Skriv "lav CO2 kan ikke trumfe levetid" heller enn abstrakt
bærekraftsretorikk.
