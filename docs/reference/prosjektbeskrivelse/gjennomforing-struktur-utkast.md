# VERIFIED — Gjennomføring, arbeidspakker og organisering

**Formål:** innsettingsklar kvalitetsløfting av gjennomføringsdelen i søknadskandidat v0.9. Teksten overfører styrken fra referansesøknadenes prosjektlogikk – tydelig arbeid, ansvar, leveranser, porter og risikohåndtering – uten å endre VERIFIEDs FoU-påstander eller gjette partnernavn, tall eller rettigheter.  
**Avgrensning:** erstatter ikke K1–K4 eller V1–V3. Uutfylte faktiske opplysninger står åpne til de bekreftes; de er ikke grunn til å stoppe eller omskrive resten av søknaden.

## Gjennomføring og organisering

Prosjektet organiseres som et trinnvis FoU-løp. Hver arbeidspakke reduserer en konkret usikkerhet før neste hovedsteg tas. Det bygges ikke en full produktplattform i prosjektet. Arbeidet avgrenses til den demonstratoren, dokumentasjonen og piloteringen som trengs for å undersøke FoU-spørsmålene.

Den juridiske prosjektansvarlige næringsaktøren har ansvar for framdrift, økonomi, sammenheng mellom arbeidspakkene og avgrensningen mot ordinær produktutvikling. Forskningspartneren har ansvar for forskningsdesign, metodevalg og vurdering av datagrunnlaget. Pilotaktører bidrar med reelle løsningsvalg, arbeidsmåter og tilbakemeldinger. Data- og produktaktører bidrar med relevante datakilder og teknisk gjennomføring innenfor avtalte rettigheter.

Faktisk organisering, ressursinnsats og partnernavn fylles inn når de er bekreftet.

| Arbeidspakke | Formål | Hovedleveranse | Port før neste hovedsteg |
|---|---|---|---|
| WP1 Styring, krav og forskningsbaseline | Avgrense prosjektet og låse forsknings- og målelogikken | prosjektkart, rollemodell, protokoll, målepunktregister og risikobilde | én avgrenset pilotramme, godkjent baseline og tydelige roller |
| WP2 Data og dokumentasjonstillit | Avklare hvilke data som er tilgjengelige tidlig nok, og hvordan kvalitet og mangler vises | datadictionary, provenansmodell, minimumsinformasjonsgrunnlag og regler for datastatus | minst to reelle alternativer kan beskrives med synlig kilde- og datastatus |
| WP3 Beslutningsmodell og usikkerhet | Utvikle og begrunne en forklarbar måte å sammenligne kriterier på | metodevalg, vektingsregler, sensitivitetsanalyse og forklaringsformat | resultatet kan spores til data, kriterier, vekter og usikkerhet |
| WP4 FoU-demonstrator og integrasjon | Vise at data, modell og forklaring kan brukes som en sammenhengende og sporbar kjede | enkel testflate, input-/output-kontrakt og eksport av sammenligningsgrunnlag | ett reelt løsningsvalg kan gjennomføres og gjentas med samme forutsetninger |
| WP5 Pilot og beslutningseffekt | Undersøke hvordan entreprenør og kunde bruker beslutningsgrunnlaget | pilotprotokoll, pilotdata, analyse og dokumenterte forbedringsbehov | funn er tilstrekkelige innenfor avgrenset scope og skilt fra hypoteser |
| WP6 Overførbarhet og robusthet | Undersøke hva som er generelt i metoden og hva som avhenger av kategori | avgrenset test i ny kategori og matrise for gjenbrukbare og kategoriavhengige deler | begrensninger, nye datakrav og muligheter for overføring er dokumentert |
| WP7 Utnyttelse, IPR og videreføring | Avklare rettigheter og legge grunnlag for videre produkt- og markedsløp | IPR-/datarettighetsmatrise, produktiseringsgap og videreføringsplan | FoU-resultater og ordinær produktutvikling er tydelig skilt |

## Metode og beslutningsporter

Arbeidet starter med krav, data og forskningsbaseline. Først når datagrunnlaget er tilstrekkelig beskrevet, utvikles og prøves beslutningsmodellen. Demonstratoren brukes til å teste den avgrensede forskningsmodellen; den er ikke en ferdig kommersiell løsning.

Piloteringen sammenligner ordinær arbeidsmåte med bruk av beslutningsgrunnlaget i samme type løsningsvalg. Prosjektet registrerer blant annet tidsbruk, forståelse, synlige datamangler, valg eller bekreftelse av valg og begrunnelse for hvordan grunnlaget ble brukt. Hvilke parametere som blir primære, og hvordan de analyseres, fastsettes i forskningsprotokollen før pilotering.

Resultater om klima, kostnader, levetid og teknisk egnethet holdes metodisk atskilt:

- direkte observerbare forhold måles i pilotene,
- modellresultater beregnes ut fra dokumenterte forutsetninger,
- framtidige eller usikre størrelser estimeres,
- teknisk egnethet vurderes faglig når dette kreves.

Usikre eller manglende data skal være synlige i sammenligningen. Modellen skal ikke fatte beslutningen på vegne av entreprenør eller kunde.

## Roller og ansvar

| Område | Prosjektansvarlig næringsaktør | Forskningspartner | Pilotaktør | Data-/produktaktør | Kunde/sluttbruker |
|---|---|---|---|---|---|
| Scope, budsjett og framdrift | A/R | C | C | C | I |
| Forskningsdesign og protokoll | C | A/R | C | I | I |
| Data og dokumentasjonstillit | A | C | C | R/C | I |
| Beslutningsmodell | R | A/R | C | C | I |
| Demonstrator | A/R | C | C | C | I |
| Pilot og analyse | A | R/C | R | C | R/C |
| IPR og videreføring | A/R | C | C | C | I |

**A** = har det endelige ansvaret. **R** = utfører. **C** = rådspørres. **I** = holdes orientert.

## Risiko og avgrensning

Prosjektet styrer særlig risiko knyttet til for bredt scope, svakt eller sent datagrunnlag, ubegrunnet vekting, pilotering uten baseline, få egnede case og uklare rettigheter. Risikoen reduseres gjennom en avgrenset FoU-demonstrator, synlige datamangler, metodekrav og sensitivitetsanalyse, forhåndsdefinert pilotprotokoll samt tidlig avklaring av roller og data-/IPR-rettigheter.

Banksporet holdes avgrenset. Det kan bare inngå som et sekundært FoU-spørsmål dersom en bank definerer et konkret informasjonsbehov og kriterier for en avgrenset utprøving. Prosjektet omfatter ikke personprofilering eller automatisk kredittbeslutning.

## Utnyttelse og videreføring

FoU-prosjektet skal gi et dokumentert grunnlag for videre utvikling av en beslutningsmodell og en mulig produktisering. Prosjektet finansierer og tester FoU-beviset. Ordinær produksjonsutvikling, bred integrasjon, kommersielt brukergrensesnitt og skalering holdes utenfor den kritiske prosjektstien og planlegges som et etterfølgende løp.

Før oppstart av pilotering avtales hvem som eier eksisterende bakgrunnsmateriale, hvem som får bruke prosjektresultater, hvilke data som kan deles, og hvordan konfidensiell prosjektinformasjon håndteres.

## Uavklarte felt som må fylles inn før innsending

1. Navn og juridisk status for prosjektansvarlig, forskningspartner, pilotaktører og eventuelle data-/produktaktører.
2. Første konkrete pilotkategori og de reelle løsningsalternativene.
3. Forskningsprotokoll, baseline, utvalg, analyseplan og primære målepunkter.
4. Milepæler med datoer, ressurser og ansvarlig partner.
5. Budsjett nedenfra: aktivitet → partner/person → timer og kostnad → arbeidspakke.
6. Endelig IPR-/datarettighetsmatrise og avgrensning av banksporet.
