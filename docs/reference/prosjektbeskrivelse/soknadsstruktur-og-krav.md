# VERIFIED — søknadsstruktur og krav til detaljnivå

**Formål:** Denne filen er søknadsarkitekturen for VERIFIED. Den overfører kvalitetsnivået i referansesøknadene til vår søknad: en evaluator skal raskt forstå problemet, FoU-usikkerheten, metoden, hvem som gjør hva, hvordan virkninger måles og hvorfor prosjektet kan gjennomføres.

Den erstatter ikke den kanoniske søknadsteksten v0.9. Den styrer hva som må inn når v0.9 videreutvikles. Ubekreftede fakta skal stå som utfyllingsfelt eller tas ut; de skal aldri erstattes med antakelser.

## 1. Hovedlogikken søknaden skal bære

`dokumentert problem → avgrenset FoU-usikkerhet → forskningsspørsmål → metode og data → arbeidspakke → leveranse/gate → pilotmåling → virkning og videreføring`

Hvert ledd må kunne spores begge veier. En leser skal kunne peke på ett FoU-spørsmål og finne:
- hvilken arbeidsoppgave som undersøker det,
- hvilke data og hvilken metode som brukes,
- hvem som har faglig ansvar,
- hva som teller som et resultat,
- hvordan resultatet skal prøves i pilot,
- hva som fortsatt er usikkert etter prosjektet.

## 2. Felles krav til hele søknaden

| Krav | Konkret betydning i VERIFIED |
|---|---|
| Én rød tråd | Tilbudsfasen, løsningsvalg og forklarbar sammenligning skal være det samme problemet i alle deler. |
| FoU, ikke produktpresentasjon | Beskriv hva prosjektet skal finne ut og teste; ikke lov full plattform, automatisk beslutning eller kommersielle funksjoner som ikke er nødvendige for FoU-beviset. |
| Presis evidens | Skill alltid mellom målt, beregnet, estimert og faglig vurdert. |
| Sporbarhet | Påstander i K1–K2 må ha kilde; krav i K3–K4 må ha metode, data og målepunkt. |
| Konkret, men nøktern | Bruk reelle aktiviteter, leveranser og beslutningsporter. Unngå generelle ord som «samarbeide», «utforske» og «videreutvikle» uten å si hva som gjøres. |
| Ingen oversalg | Ikke skriv at VERIFIED forbedrer klima, økonomi eller bankvurdering. Skriv hva pilotene skal undersøke og hvilke avgrensninger som gjelder. |
| Samme begreper | Bruk «løsningsvalg», «sammenligning», «beslutningsgrunnlag» og «tilbudsfasen» konsekvent. |

## 3. Krav per del i søknaden

### Sammendrag

Må svare på fem setninger:
1. Hva er beslutningsproblemet i tilbudsfasen?
2. Hva er FoU-usikkerheten som dagens løsninger ikke svarer på?
3. Hva utvikles og testes?
4. Hvor og med hvem prøves det?
5. Hvilken praktisk nytte undersøkes?

Hold det på prosjektets nivå. Ikke ta med partnernavn, effektstørrelser eller tekniske løsningsdetaljer som ikke er bekreftet.

### K1 — Bakgrunn og utfordring

Må dokumentere at problemet er reelt og relevant.

**Skal inneholde**
- tydelig situasjon: mindre entreprenører skal sammenligne alternative løsninger før tilbudet låses,
- hvorfor tilgjengelig informasjon er spredt, ulik og vanskelig å bruke samlet,
- relevant og nøkternt kunnskapsgrunnlag om målgruppe og kontekst,
- konsekvensen av svakt sammenligningsgrunnlag, uten å påstå størrelsen på effekten.

**Må ikke gjøre**
- gjøre en generell bransjeutfordring om til en dokumentert VERIFIED-effekt,
- bruke uverifiserte bransjetall,
- blande tilbudsfasen med senere prosjekterings- eller driftsfase.

### K2 — Nyhetsverdi og kunnskapsstatus

Må vise både hva som allerede finnes og hva VERIFIED faktisk skal finne ut.

**Skal inneholde**
- avgrenset oversikt over relevante standarder, metoder og eksisterende løsninger,
- hva disse løser og hva de ikke dokumenterer innenfor VERIFIEDs brukssituasjon,
- ett klart forskningshull per hovedusikkerhet,
- forsiktig avgrensning mot konkurrenter: «ikke dokumentert i utvalget» heller enn «finnes ikke».

**Detaljkrav**
- Hver sammenligning må ha samme dimensjoner: tidspunkt i arbeidsprosessen, data, kriterier, usikkerhet, forklaring og faktisk bruk.
- Nyhetsverdien skal ligge i kombinasjonen som testes: datatilgjengelighet, dokumentasjonstillit, avveiing og beslutningseffekt.

### K3 — Mål og FoU-spørsmål

Må gjøre prosjektet testbart.

**Skal inneholde**
- ett hovedmål som beskriver den avgrensede beslutningsmodellen,
- 3–4 delmål som kan gi konkrete leveranser,
- F1–F6 i formuleringer som kan undersøkes,
- kobling fra hvert FoU-spørsmål til data, metode, WP, målepunkt og pilot.

**Kvalitetskontroll**
Et FoU-spørsmål er godt nok først når det ikke kan besvares med «vi bygger en funksjon». Det må kreve en metode, empirisk prøving eller begrunnet analyse.

### K4 — Metode, pilot og forskningsetikk

Må forklare hvordan prosjektet skal redusere usikkerheten.

**Skal inneholde**
- trinnvis metode: datagrunnlag → modell → demonstrator → pilot → analyse → justering,
- minste informasjonsgrunnlag og tydelig håndtering av manglende eller svake data,
- kriterier for valg av flerkriteriemetode og sensitivitetsanalyse,
- pilotdesign med baseline, utvalg, analyseplan og dokumentasjon av avvik,
- skille mellom målt, beregnet, estimert og faglig vurdert,
- datahåndtering, personvern og kommersielt sensitive data.

**Minimum pilotprotokoll**
| Element | Må beskrives før innsending |
|---|---|
| Case | Én produktkategori og 2–4 reelle løsninger/alternativer |
| Baseline | Hvordan samme type løsningsvalg håndteres uten VERIFIED |
| Målepunkt | Tidsbruk, forståelse, datamangler, valg/bekreftelse og begrunnelse |
| Datakilder | Hvilke kilder brukes, tilgang og dokumentasjonsstatus |
| Analyse | Hva sammenlignes, og når er data for svake til å tolkes |
| Etikk | Deltakerinformasjon, minimering av persondata og håndtering av sensitiv informasjon |

### V1 — Miljø og bærekraft

Må beskrive virkningsmekanismen uten å overselge effekt.

**Skal inneholde**
- hvorfor bedre sammenligning kan støtte ressursbruk og mindre avfall,
- hvilke deler av virkningen som kan beregnes, estimeres eller bare undersøkes,
- sammenligningsgrunnlag for klima, materialbruk, levetid, vedlikehold og livsløpskostnad,
- tydelig tidshorisont: kort pilot kan ikke dokumentere langsiktige byggskader eller reklamasjoner.

### V2 — Do-no-harm

Må vise at negative konsekvenser er håndtert som en faglig del av modellen.

**Skal inneholde**
- teknisk egnethet som en egen port, ikke bare en poengsum,
- synlig usikkerhet, dokumentasjonskrav og faglig vurdering,
- avgrenset vurdering av ombruk, reparasjon, rehabilitering og nyanskaffelse,
- konkrete DNSH-forhold fra partnerne før innsending.

### V3 — Økonomiske virkninger og bankrelevans

Må vise en plausibel, men avgrenset vei fra FoU til nytte.

**Skal inneholde**
- mekanismen: bedre sammenligning av anskaffelse, vedlikehold og beregnede utskiftninger,
- separate hypoteser for entreprenør, kunde og eventuell bank,
- banksporet som et avgrenset informasjonsbehov – aldri som kredittmodell eller dokumentert risikoeffekt,
- hva som må være definert av en bank før bankrelevans kan undersøkes.

### Gjennomføring, arbeidspakker, budsjett og organisering

Bruk [gjennomforing-struktur-utkast.md](gjennomforing-struktur-utkast.md) som innsettingsgrunnlag.

**Skal inneholde**
- WP1–WP7 med formål, aktiviteter, leveranse, ansvarlig rolle, avhengighet og exit-gate,
- RACI som viser hvem som har beslutningsansvar, utfører og bidrar,
- milepæler som dokumenterer endret modenhet, ikke bare «arbeid utført»,
- risiko med sannsynlighet, konsekvens, eier og tiltak,
- budsjettlogikk nedenfra: aktivitet → person/partner → time/kostnad → WP,
- skille mellom FoU-demonstrator og ordinær produktutvikling,
- IPR-, data- og utnyttelsesprinsipper.

## 4. Detaljer som må hentes inn før endelig søknad

Dette er et innhentingsbehov, ikke et krav om å gjette nå.

| Tema | Konkret informasjon som må inn |
|---|---|
| Konsortium | juridisk prosjektansvarlig, FoU-partner, pilotaktører, data-/produktaktører og rolle per aktør |
| Pilot | første kategori, alternativer, tilgjengelige case, rekruttering og reservecase |
| Ressurser | timer, kostnadstype, WP-ansvar og faktisk bidrag per partner |
| Metode | forskningspartnerens metodevalg, baseline, utvalg og analyseplan |
| Data | kilde, tilgang, rettighet, kvalitet/status, personvern og lagring |
| Utnyttelse | bakgrunns-IPR, forventede FoU-resultater, tilgang og videre produktløp |
| Risiko | partneravhengigheter, datahull, metode-/vekting, pilotgjennomføring og avgrensning mot produktutvikling |
| DNSH | material-/kjemikalieforhold, sosiale hensyn og øvrige prosjektrelevante risikoer |

## 5. Siste kvalitetssjekk før innsending

Søknaden er klar til redigering inn i skjemaet når følgende kan besvares kort og konsistent:

1. Hvilket konkret løsningsvalg i tilbudsfasen undersøker dere?
2. Hvilken usikkerhet kan ikke løses med eksisterende metode eller verktøy?
3. Hvilket FoU-spørsmål undersøker hver arbeidspakke?
4. Hvem gjør arbeidet, med hvilken kompetanse og ressurs?
5. Hvilket datagrunnlag brukes, og hvordan vises svakheter?
6. Hva viser at demonstratoren er klar for pilot?
7. Hvordan måles bruk, forståelse og beslutningseffekt?
8. Hva er FoU-resultat, og hva er etterfølgende produktutvikling?
9. Hvilke virkninger er målt, beregnet, estimert eller fortsatt hypotetiske?
10. Hvilke risikoer kan velte gjennomføringen, og hvem eier tiltaket?

Hvis ett spørsmål bare kan besvares med generell prosa, mangler søknaden fortsatt detaljgrunnlag.
